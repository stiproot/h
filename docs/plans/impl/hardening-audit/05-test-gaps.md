## [x] A14. The /setup spec-hash idempotency sentinel is untested in BOTH stacks

*Severity: medium · effort: small*

**Gap:** The idempotent-setup contract — hash the setup spec, short-circuit when the sentinel matches, re-provision when the spec changes — is implemented twice (JS agent-routes.ts, Python routes.py) and tested nowhere: JS agent-server's three test files cover run-handler, run-ledger, and workflow-babysitter only; Python's cover workflow_route only. This is the mechanism that makes reusable workspaces (workspaceId, every cron/recurring run) safe; a regression either re-runs arbitrary setup commands on every cron fire or, worse, skips provisioning after a spec change (stale skills/plugins for all subsequent runs).

**Evidence:** `/home/stiproot/code/h/packages/js/agent-server/src/agent-routes.ts:35 (SETUP_SENTINEL), :180-204 (hash compare + sentinel write)` · `/home/stiproot/code/h/packages/py/agent-server/src/agent_server/routes.py:104-107 (sorted-keys json hash, sentinel.read_text() == spec_hash short-circuit), :128 (sentinel written after steps)` · `/home/stiproot/code/h/packages/js/agent-server/src (only run-handler.test.ts, run-ledger.test.ts, workflow-babysitter.test.ts)` · `/home/stiproot/code/h/packages/py/agent-server/tests (only test_workflow_route.py)`

**Do:** Add a setup-idempotency spec in each stack against the same four scenarios. JS: packages/js/agent-server/src/agent-routes.test.ts (vitest, beside the existing three test files) — exercise the /setup route via Fastify inject with a stubbed command runner and a tmp workspace resolver (or test the setup Effect directly with a mocked FileSystem layer, matching how run-handler.test.ts isolates effects).
